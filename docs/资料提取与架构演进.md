# 数据提取与架构演进

## 当前边界

`app.js` 只负责页面、军表状态、数据加载和将用户选择转换为计算输入。它不应保存阵营的单位数值、武器列表或技能结算细节。

| 层 | 位置 | 责任 |
| --- | --- | --- |
| 原始资料与结构化数据 | `data/<阵营>/` | 单位属性、武器、装备、原文、页码与版本 |
| 阵营/单位/分遣队规则 | `rules/<阵营>.js` | 原文、条件、可选控件与声明式效果 |
| 星际战士规则目录 | `rules/space-marines.js` | 由 `tools/generate-space-marine-rules.mjs` 从全部数据卡生成；保留 92 个可载入单位的原文技能，已支持的战斗效果使用统一注册表 |
| 死亡守卫规则目录 | `rules/death-guard.js` | 由 `tools/generate-death-guard-rules.mjs` 从 `死亡守卫-全部数据卡.json` 生成；覆盖 36 张数据卡，纳垢赐福使用统一的目标韧性修正效果 |
| 通用效果注册表 | `rules/effects.js` | 将 `effect.type` 转换为中立的攻击/防御修正 |
| 通用规则解析 | `rules/resolver.js` | 收集规则、处理条件和调用效果注册表 |
| 骰子计算 | `engine.js` | 概率和伤害模拟；不依赖阵营、单位或技能名 |
| 页面与交互 | `app.js` | 选择单位、编辑武器/模型、显示可选技能、组装引擎输入 |

禁军现在使用 `data/帝皇禁军/帝皇禁军-结构化数据卡.json` 作为计算数据来源；OCR 索引与可检索 Markdown 只用于原文溯源和 AI 检索。

## 给其他 AI 的提取任务

模板文件是 `data/模板/数据卡模板.json`。提取 AI 必须输出单个、可被 `JSON.parse` 读取的 JSON 文件，不要输出 Markdown 表格或解释段落。

可直接使用下面的指令：

```text
请从所给 Warhammer 40,000 数据卡 PDF 提取全部单位，严格按“数据卡模板.json”的 schema 输出合法 JSON。

规则：
1. 每一页/每个单位都必须提取，不能只提取第一个单位。
2. 属性必须分别填写 models、movement、toughness、save、invulnerableSave、woundsPerModel、leadership、objectiveControl。
3. W 是每个模型的 woundsPerModel；看不清时填 null 并设置 extraction.needsReview=true，绝不默认填 1。
4. 每种武器模式单独列出；同一把武器只能选一种模式时填写相同 selectionGroup，不能把不同模式合并为同时攻击。
5. 技能、装备选项、领袖限制必须保留完整原文，不能概括或补写规则；每条技能写入 abilities，并附 category、condition、phase、uses、status。
6. 记录 PDF 文件名、版本、页码和原始 OCR 文本；数值应优先以可见表格为准。
7. 不确定的数据填 null / needsReview，不得猜测；不要把 OCR 识别错误伪装为确定数值。
8. 输出前检查 JSON 可解析、单位名不重复、每个武器都有 type、attacks、skill、strength、ap、damage。
```

## 数据约定

- `unit.defaultEquipment` 是纯数据卡被选中时的默认装备；军表被选中时始终以军表的实际装备与存活模型数为准。
- `models` 是默认整队模型数，`woundsPerModel` 是每个模型的 W 值，两者不能混用。
- 如果一个单位内部有冠军/队长与普通队员，使用卡片级 `modelProfiles` 拆分成员。固定成员填写 `id`、`name`、`role`、`count`；剩余普通成员填写 `remaining: true`。每个 profile 可有独立 `defaultEquipment`、`weaponNames`、`unit` 覆盖和 `weaponMultipliers`（例如队长额外一把武器）。未填写 `modelProfiles` 的单位继续按单一模型组处理。
- `invulnerableSave` 没有特殊保护时填 `null` 或 `0`，不能填普通护甲值。
- `type` 只能是 `ranged` 或 `melee`。
- `attacks` 与 `damage` 可为 `"d6"`、`"d6+1"` 等表达式；`skill` 保留 `"2+"` 或 `"torrent"`。
- 同名武器的射击和近战档必须各自一条，因为它们是不同攻击档。
- `abilities[].text` 必须是原文；`status` 只表示程序是否已实现，不改变原文含义。
- 阵营、单位、分遣队只是规则展示分类；是否一次性、是否需主动选择，由 `uses` 与规则模块中的控件表示。

## 新增阵营或分遣队

1. 在 `data/<阵营>/` 新增结构化数据卡 JSON，并保留 PDF/可检索原文。
2. 将文件加入 `CALCULATOR_CARD_FILES`，不把单位属性写回 `app.js`。
3. 新增 `rules/<阵营>.js`：规则项只描述原文、条件、可选项和 `effect.type`。数据卡 JSON 的 `abilities` 会先作为未实现技能原文显示；要进入计算，才在规则文件声明对应效果。
4. 如果 `effect.type` 是通用效果（重投、命中修正、不知疼痛、伤害覆盖等），在 `rules/effects.js` 增加一次通用处理；不要把单位名写入 `engine.js`。
5. 只有该技能确实影响当前“射击/近战伤害计算”时才实现效果；其余保持 `displayOnly`，但仍显示原文。
   星际战士同样遵循此边界：移动、部署、CP、复活、震慑和一次性战术先保留原文；命中/造伤修正、重投、连击、致命一击、毁灭伤害、不知疼痛和特殊保护可由玩家勾选后进入计算。
6. 为复杂技能增加最小回归用例，再提交。

星际战士的规则目录由 `tools/generate-space-marine-rules.mjs` 生成；首次从 PDF/Markdown 补齐缺失技能时运行 `node tools/generate-space-marine-rules.mjs --write-source`，会把补齐后的原文同步回结构化数据卡，再生成 `docs/rules/space-marines.js`。

死亡守卫使用 `tools/extract_death_guard_pdf.py` 从数字版 PDF 提取跨页数据卡表格，输出 36 张结构化数据卡、按页可检索 Markdown 和分数表；随后运行 `node tools/generate-death-guard-rules.mjs` 生成规则目录。纳垢赐福的目标T-1与三选一瘟疫由同一个规则控件驱动，头骨痉挛和颤骨瘟疫会进入伤害计算，烂魂伤风保留为说明。技能原文始终保留，暂未映射到通用效果的技能仍以“已显示，暂不改变本次骰子”呈现；军表详情优先使用结构化 JSON 渲染属性与武器卡片，Markdown 仅作为回退资料。

## 回归防护

执行：

```powershell
node tools/validate-datasheets.mjs
node tools/validate-rules.mjs
node --check docs/app.js
node --check docs/engine.js
node --check docs/rules/custodes.js
node --check docs/rules/space-marines.js
node --check docs/rules/death-guard.js
node --check docs/rules/resolver.js
```

数据校验会严格检查新的结构化卡：覆盖、必填属性、非零 W 值、武器档、剑锋冠军的互斥武器模式，以及规则模块中已纠正的阿拉鲁斯/终结者连长不知疼痛错误。旧的星际战士提取卡会输出缺字段警告，不会阻止现有页面继续使用其 Markdown 回退。

每次修复都应使用能说明问题的 Git 提交信息。现有相关历史可以用 `git log --oneline` 查看，例如：

- `7220224`：W 值与基础计算修正；
- `767b4a3`、`a0d3c54`：联合单位结算；
- `ce58076`、`d8a868e`：星际战士/禁军武器档与互斥模式；
- `6ea26c7`：禁军技能原文与错误技能修正；
- `859f25c`：按骰面选择重投。

Git 历史能说明“为什么改”，但自动校验才负责防止同类问题在重构时回归。
