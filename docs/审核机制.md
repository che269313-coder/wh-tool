# 变更审核机制（Change Audit Protocol）

> 用途：每次**架构重构、新增阵营、新增功能**等大改动完成后，例化多个 subagent **并行**审核，输出统一的 ❌/⚠️/✅ 报告，经人工审查后修复。
> 原则：**实现与审核分离**——重构/开发可以交给任何模型（如 fable5），审核固定由擅长代码审查与修复的模型（如 deepseek-v4-flash）执行。
> 参考：2026-08-08 首轮审核（7 个 subagent 并行）的维度划分与报告格式，报告样例见 `docs/audit/`。

---

## 一、触发时机

满足任一即触发完整审核：

- 架构重构完成（合并代码后）
- 新增阵营/新增单位数据入库
- 新增功能（引擎、计算器、导入、UI 行为）
- 生成器/提取脚本改动
- 数据卡批量修复

小改动（单条规则、单个数据字段）不触发完整审核，仅跑 `validate-*.mjs` 三件套。

---

## 二、审核维度（subagent 分工）

完整审核默认拆分为 **7 个并行 subagent**，互不共享上下文（防污染）：

| # | 维度 | 覆盖内容 | 对照源 | 输出文件 |
|---|---|---|---|---|
| 1 | 星际战士数据卡核对 | 卡名/属性/关键词/武器/abilities 与水印、杂散数字、特殊保护 | PDF vs JSON vs catalog | `sm-datasheet-audit.md` |
| 2 | 死亡守卫+禁军数据卡核对 | 同上（含跨页表、重复卡、页码） | PDF vs JSON | `dg-custodes-datasheet-audit.md` |
| 3 | 武器词条 vs 外部计算器 | 全部 abilities 词条（连击/致命/毁灭/反X/双联/torrent/重投…）本地引擎 vs Wathammer 对比 | engine.js + wathammer.com/simulate-round | `weapon-keywords-audit.md` |
| 4 | 星际战士技能实现核对 | 每个单位每条规则的原文 vs effects/controls/status | rules/*.js + PDF | `sm-skills-audit.md` |
| 5 | 星际战士兵种技能核对 | 同上（兵种/载具） | 同上 | `sm-squads-audit.md` |
| 6 | 死亡守卫技能实现核对 | 同上 | 同上 | `dg-skills-audit.md` |
| 7 | 禁军技能实现核对 | 同上 | 同上 | `custodes-skills-audit.md` |

> 维度 1/2 按阵营合并以控制 subagent 数；阵营更多时可再拆分（每阵营一个）。

## 三、执行流程

```text
[1] 跑脚本基线
    node tools/validate-rules.mjs
    node tools/validate-combat.mjs
    node tools/validate-datasheets.mjs
    （若改动涉及引擎/计算器：抽样场景对比 wathammer.com/simulate-round）

[2] 例化 N 个 subagent 并行审核
    每个 subagent 使用下方"subagent 任务模板"，只做研究与报告，
    禁止修改项目文件；报告写入 docs/audit/<日期>-<主题>/

[3] 汇总（主审核员）
    读取全部报告，合并 ❌ 清单、⚠️ 存疑清单、✅ 统计；
    剔除误报与已知例外（如污染者、狮门英杰、扭颅疫病近战限定）。

[4] 人工审查
    用户逐条确认 ❌ 清单（技能语义以用户理解为准，AI 不擅自修规则）。

[5] 修复 + 回归
    按用户批准清单修复；重新跑 [1] 全部校验 + 补回归断言。

[6] 报告归档
    本次审核结论写入 docs/audit/<日期>-<主题>/summary.md。
```

## 四、subagent 任务模板（可直接复用）

每个 subagent 的 prompt 按以下骨架填充（维度、阵营、对照源按表二替换）：

```text
你是规则/数据审计员。项目在 C:\Users\che26\Desktop\wh-tool（战锤40k计算器）。
任务：<维度描述，如"逐一核对星际战士所有单位的技能原文与其计算实现是否有偏差">。
只做研究和报告，禁止修改项目任何文件。

## 数据源
- <规则目录>: docs/rules/<faction>.js（text/status/controls/effects 字段说明）
- 效果注册表: docs/rules/effects.js（每个 case 一种 effect.type）
- 数据卡原文: docs/data/<阵营>/*.md 与 *.json
- PDF 原文（歧义时以 PDF 为准）: <pdf 路径>（Python fitz 读取，水印"老湿腐战锤群 52110733"剔除）

## 参考历史 bug（这些出过不止一次）
先运行 git log --all --grep="fix|修复" -i --format="%h %s" 查看历史修复，
重点重现检查：<历史 bug 清单，如 水印残留/杂散数字/特殊保护误提取/关键词缺失/torrent 未识别/反X未解析/多实现/漏实现>。

## 核对清单
1. <具体核对项，如 status="已显示" 的技能是否本应影响骰子>
2. <数值/条件/阶段/控件是否与原文一致>
3. 每条规则给出：✅一致 / ⚠️存疑（说明理由）/ ❌偏差（原文 vs 实现）

## 输出
写到 C:\Users\che26\Desktop\wh-tool\docs\audit\<日期>-<主题>\<文件名>.md：
- 表格：| 单位 | 规则 | 原文摘要 | status | 实现 | 结论 | 说明 |
- 末尾汇总：总数、✅/⚠️/❌ 数量、❌ 完整清单（原文+实现摘录）
❌ 和 ⚠️ 必须给出可判断依据，不要臆断。最终消息里报告数字和 ❌ 清单摘要。
```

## 五、回归维度：历史 bug 复查（每次必做）

审核时额外要求每个 subagent 检查"本次改动是否复现了历史 bug"。历史来源：

1. `git log --all --grep="fix|修复"` 的提交（当前 30+ 条）
2. `docs/bug-report/` 结构化报告（含死亡寿衣反步兵案例）
3. 上一轮 `docs/audit/` 全部 ❌ 项

复查项模板（嵌入 subagent prompt）：

```text
## 历史 bug 清单（逐项确认未复现）
- 水印残留（老/湿/腐/战/群/锤 字符进入 abilities/装备/武器名）
- abilities 杂散数字前缀（"3 手枪"）
- 特殊保护 X+ 被误提取为别的值 / 被动值被一次性值污染
- 关键词字段缺失
- torrent 未识别 / 反X N+ 未解析（含反飞行/反灵能者）
- 多实现（超出原文的效果） / 漏实现（本应进骰子却"已显示"）
- 规则 ID/单位名硬编码导致校验脆弱
```

---

## 六、验收标准

一次审核"通过"需同时满足：

1. `validate-*.mjs` 三件套零失败
2. 全部 subagent 报告 ✅/⚠️/❌ 已汇总，❌ 项已获用户逐条确认
3. 修复后重新跑 [1] 通过，且为每个修复项补了回归断言
4. 历史 bug 清单逐项确认未复现（有复现的必须修复并补断言）
5. 报告归档到 docs/audit/<日期>-<主题>/

---

## 七、轻量审核（不改规则数据时）

仅改动 UI/引擎且不影响数据与规则时，可只跑 3 个 subagent：

- 武器词条 vs 外部计算器（引擎改动必跑）
- 受影响阵营的技能核对（规则/数据改动必跑）
- 功能行为审查（新功能：构造典型场景跑通 + 边界用例，报告行为是否符合预期）
