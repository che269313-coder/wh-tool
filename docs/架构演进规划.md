# 架构演进规划：数据解耦与可扩展性路线图

> 目的：随着阵营、单位、技能越来越多，把项目从"提取一次 + 正则猜词 + 手写契约"的脆弱模式，演进为"数据驱动 + 单一词典 + 自动对账"的清晰结构。
> 背景依据：`docs/audit/` 下的 7 份审计报告（数据卡属性、武器词条 vs 外部计算器、三方技能实现偏差）暴露的重复性缺陷。

---

## 一、现状问题（共性结论）

审计发现同类 BUG 反复出现，根因都是同一批架构弱点：

| # | 弱点 | 表现 | 典型案例 |
|---|---|---|---|
| 1 | 提取一次，无人复核 | 水印/杂散数字/特殊保护被吞/缺武器行 | 莱山德 invuln=2、26 张英雄卡特殊保护丢失 |
| 2 | 正则散落在多处 | app.js、两个生成器、修复脚本各写一套 | 反飞行/反灵能者漏识别、`结 果`/`疼 痛` 空格变体漏匹配 |
| 3 | 效果注册表靠 case 堆积 | 新效果类型要改 4~6 处文件才接通 | damage-reroll 曾有引擎能力却未接线 |
| 4 | 双份默认值 | engine 与 app.js 各维护一份 effect 默认字段 | 深渊之女 Math.max 语义冲突 |
| 5 | 校验脚本硬编码 | ID/单位名写死，规则一生成就碎 | 高举旗帜 p85-3、泰图斯"核心特性"断言失效 |
| 6 | 别名/阵营散落硬编码 | resolver.js 里的别名表与正则链 | 戒卫者/警戒者重复卡、百骑长改名连锁 |
| 7 | 文本→效果无中间层 | 技能语义靠人工判断"已显示 vs 计算支持" | 牧师憎恨祷言漏实现、豪猪多实现命中重投 |

---

## 二、重构目标

1. **单一真相源**：一个词条词典、一份 payload schema、一份默认值。
2. **新增成本可预期**：新阵营 = 数据卡 JSON + 词条引用，不需要碰引擎。
3. **错误在源头被发现**：PDF↔JSON↔规则 三层对账全部脚本化。
4. **任何一步可回退**：每阶段都有 validate-*.mjs 收口。

---

## 三、实施路线（按收益排序，每阶段独立可交付）

### 阶段 1：统一词条字典（最高优先）

**问题**：`docs/app.js` 的 `weaponEffectsFromKeywords`、`tools/generate-space-marine-rules.mjs`、`tools/generate-death-guard-rules.mjs`、`tools/reconcile_sm_invulnerable_saves.py` 各自维护一套"中文技能词 → 效果"正则。

**方案**：新建 `docs/rules/keyword-dictionary.js`，只做一件事——把技能短语映射为结构化效果：

```js
// 最长短语优先匹配；每个词条配一个测试样例
const KEYWORD_DICTIONARY = [
  { pattern: /连击\s*(d3|\d+)/, make: (m) => ({ type: "sustained-hits", value: m[1] || 1 }) },
  { pattern: /致命(?:一击|命中)/, make: () => ({ type: "lethal-hits" }) },
  { pattern: /反(步兵|载具|巨兽|工事|泰坦级|飞行|灵能者)\s*([2-6])\+/, make: (m) => ({ type: "anti-keyword", target: m[1], threshold: Number(m[2]) }) },
  { pattern: /双联/, make: () => ({ type: "twin-linked" }) },
  // ... 全部词条
];
```

- app.js 运行时解析、两个生成器、`validate-rules.mjs` 全部消费同一词典。
- 新增阵营/新词条 = 加一行 + 一条测试样例。
- 反飞行/反灵能者这类缺口不会再出现（词典里本来就声明了目标关键词）。

**涉及文件**：新建 `docs/rules/keyword-dictionary.js`；`app.js`、两个生成器改为引用；`validate-rules.mjs` 加"词典覆盖率"断言。

**验收**：跑通 `node tools/validate-combat.mjs` + 词典词条级回归（每个词条一个 payload 用例 vs Wathammer）。

---

### 阶段 2：数据卡 schema v2 + 对账管线

**问题**：审计证明"提取一次"不可靠；`fix_datasheet_audit_issues.py` 是一次性脚本，新阵营不会再跑。

**方案**：
1. `docs/data/模板/数据卡模板.json` 升级 schemaVersion=2：武器与单位技能增加可选 `effects` 字段（提取时直接填结构化效果），`abilities` 原文保留用于展示与溯源。
2. 把 `tools/reconcile_sm_invulnerable_saves.py` 泛化为 `tools/reconcile_datasheets.py`：对每个阵营 PDF↔JSON 自动 diff——属性/武器/词条/水印/杂散数字/特殊保护/关键词，输出差异清单并可选自动修复。
3. 新阵营接入流程：提取 JSON → 跑对账脚本 → 零差异后才允许进入 catalog 生成。

**涉及文件**：`docs/data/模板/*`、`tools/reconcile_datasheets.py`、`tools/validate-datasheets.mjs`。

**验收**：`reconcile` 报告与 `validate-datasheets.mjs` 的断言互为补充，新增阵营必须同时通过两者。

---

### 阶段 3：效果注册表 schema 化

**问题**：`docs/rules/effects.js` 每个 case 是自由手写；新效果类型要动 effects.js + app.js + engine.js + 生成器 + 校验，漏一处就断线（damage-reroll 曾闲置）。

**方案**：把 effect.type 声明为 schema：

```js
const EFFECT_SCHEMAS = {
  "hit-modifier":     { fields: ["value"], conditions: ["underStartingStrength", "belowHalfStrength", "targetBelowHalf", "large-or-led"], sides: ["attack"] },
  "damage-minus":     { fields: [], conditions: [], sides: ["attack"] },
  "save-bonus-vs-d1": { fields: [], conditions: [], sides: ["defend"] },
  // ...
};
```

- 新增 `tools/validate-effects.mjs`：遍历全部规则文件，检查——每个 effect.type 都有 schema；必填字段齐全；条件枚举合法；sides 与消费方（app.js/engine.js）已接线。
- 效果→引擎字段的映射集中为一个纯函数 `effectsToPayload(attack, defend)`，消灭双份默认值。

**涉及文件**：`docs/rules/effects.js`、`tools/validate-effects.mjs`、`docs/engine.js`、`docs/app.js`。

**验收**：`validate-effects.mjs` 零告警；新增一个效果类型时只需改 2 处（schema + 映射函数）。

---

### 阶段 4：技能覆盖率报告

**问题**：技能"已显示 vs 计算支持"的缺口全靠人工审计（本次 3 个 subagent 手工核对）。

**方案**：生成器输出规则的同时产出 `docs/audit/skill-coverage-<faction>.md`：
- 已实现（有 effects 且已接线）
- 已显示（原文保留，未进骰子）——按"本应可计算"打分排序
- 存疑（阶段/条件/目标范围与原文有偏差）

**涉及文件**：两个生成器、`tools/validate-rules.mjs`。

**验收**：新增阵营的覆盖率报告一页纸，可计算项为零遗漏。

---

### 阶段 5：阵营注册表

**问题**：`docs/rules/resolver.js` 的别名表、阵营正则、`anathemaPsykanaUnits` 名单全是硬编码；改名/合并卡时要连锁修改（本次百骑长/阿拉琉斯/警戒者）。

**方案**：`docs/rules/registry.js` 声明式配置：

```js
const FACTIONS = {
  星际战士: { file: "rules/space-marines.js", catalog: "星际战士-全部数据卡.json", aliases: {...} },
  帝皇禁军: { file: "rules/custodes.js", ... },
  死亡守卫: { ... },
};
```

- 新阵营 = 注册一行；resolver.js 删除所有正则链与硬编码名单。
- 别名表由生成器/对账脚本维护，改名时自动产出迁移映射。

**涉及文件**：新建 `docs/rules/registry.js`、改 `resolver.js`。

---

### 阶段 6：单一 payload schema

**问题**：`engine.js` 的 `WEAPON_DEFAULTS`/`DEFENDER_DEFAULTS` 与 `app.js` 的 `emptyWeaponEffects`/`emptyDefenderEffects` 双份手写默认值，字段漂移即静默 bug。

**方案**：定义 `docs/rules/payload-schema.js`（或 JSON Schema），engine 默认值与 app.js 空效果都由它派生；`validate-combat.mjs` 校验 payload 字段与 schema 一致。

**涉及文件**：新建 `docs/rules/payload-schema.js`、改 `engine.js`、`app.js`。

---

### 阶段 7：校验去硬编码

**问题**：`validate-rules.mjs` 里规则 ID（p85-3）、单位名（"核心特性"）写死，规则一重新生成就碎。

**方案**：
- 断言一律按"规则名 + 效果类型 + 数值"定位，不再用 ID。
- 单位名断言从数据卡 JSON 推导（如"所有带特殊保护原文的单位必须有 invulnerable-save 效果"），而不是逐卡枚举。
- 新增"规则与数据卡一致性"通用断言：数据卡 `abilities` 中出现的词条，规则目录必须给出已实现/已显示之一。

**涉及文件**：`tools/validate-rules.mjs`、`tools/validate-datasheets.mjs`。

---

## 四、实施顺序建议

1. **阶段 1 + 6**（词典 + 单一 schema）：收益最大、改动集中，先做。
2. **阶段 3 + 7**（效果 schema + 校验去硬编码）：与 1、6 配套，防止重构破坏现有 30+ 条回归断言。
3. **阶段 2**（对账管线）：随新阵营接入逐步落地，每个阵营进库前必跑。
4. **阶段 4 + 5**（覆盖率报告 + 注册表）：在接入第 4 个阵营之前完成。

> 原则：每一步都以 `node tools/validate-*.mjs` 三件套 + Wathammer 外部基线对比收口，任何一步都不允许让现有已通过的计算结果回退。
